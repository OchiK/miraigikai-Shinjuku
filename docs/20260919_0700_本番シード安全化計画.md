# 本番シード安全化計画

令和8年第2回定例会の全23案件をシード側で `published` にした（#25）。この内容を本番DBへ届ける手段は現在 `seed_production.yml` しかなく、その中身は `pnpm --filter @mirai-gikai/seed seed`、つまり [packages/seed/main/run.ts](../packages/seed/main/run.ts) である。run.ts は最初に `clearAllData()` を呼ぶ。

```ts
// packages/seed/shared/helper.ts
const TABLES_TO_CLEAR = [
  "interview_report",
  "interview_messages",
  "interview_sessions",
  "interview_questions",
  "interview_configs",
  "faction_stances",
  "chats",
  "bill_contents",
  "bills_tags",
  "bills",
  "tags",
  "factions",
  "committees",
  "council_sessions",
] as const;
```

利用者が書いたインタビューの回答、レポート、AIチャットの履歴が消える。2026-09-18 の投入でも同じ手順を踏んでおり、[Step 5 本番環境検証](verification/20260918_1830_step5_production_verification.md)に「安全な本番投入としては未達」と記録してある。さらに bills を作り直すため id が変わり、既存の詳細ページURLが404になった。

したがって公開は本番専用インポーターを用意してから行う。以下はその設計である。

## 決めること

### 1. どの範囲を上書きするか

シードが持つデータは二層に分かれる。

一次資料に由来する層（council_sessions、bills、bill_contents、tags、bills_tags）は、リポジトリ側が唯一の正とみなしてよい。Admin から本番で直接編集された場合も、次回インポートで上書きされる。

利用者が作る層（interview_sessions、interview_messages、interview_report、chats、interview_rating_feedbacks、expert_registrations）は、インポーターが読むことも書くこともない。

中間にあるのが interview_configs と interview_questions である。Admin で設定を組み替える運用があるため、シードが上書きすると本番の設定を壊す。インポーターの対象から外し、開発シードだけが作る扱いにする。

### 2. 削除をどう扱うか

bills を消すと interview_configs が CASCADE で落ち、その先のセッションとレポートまで消える。インポーターは bills を削除しない。インベントリから消えた議案が本番に残っていたら、削除せずに一覧へ出力して人が判断する。

bill_contents は (bill_id, difficulty_level) が一意なので upsert で済む。難易度を減らす変更（hard を廃止するなど）は今のところ発生しないため、余った変種も削除せず報告に留める。

### 3. id を変えない方法

bills には `idx_bills_slug`（unique）がある。slug は [buildItemKey](../packages/seed/main/shinjuku-r8-2-inventory.ts) が `shinjuku-2026-r2-gian-42` の形で決めており、会期をまたいでも衝突しない。この slug を自然キーにすれば、2回目以降のインポートで id が保たれる。

他のテーブルの自然キーも揃っている。

| テーブル | 自然キー | 制約 |
| --- | --- | --- |
| council_sessions | slug | `20251215200000_add_slug_to_diet_sessions.sql` |
| bills | slug | `idx_bills_slug` |
| bill_contents | (bill_id, difficulty_level) | `20250914183213_add_bill_contents_table.sql` |
| tags | label | `20251011073735_add_tags_and_bills_tags_tables.sql` |
| bills_tags | (bill_id, tag_id) | 同上の PRIMARY KEY |

## 実装

### ファイル構成

```
packages/seed/production/
├── import.ts        # エントリポイント
├── importer.ts      # upsert 本体（副作用あり）
├── diff.ts          # 投入前後の差分を組み立てる純粋関数
└── diff.test.ts
```

`packages/seed/package.json` に次を足す。

```json
"import:production": "tsx production/import.ts",
"import:production:dry-run": "tsx production/import.ts --dry-run"
```

### upsert の流れ

```ts
// packages/seed/production/importer.ts
export async function importInventory(
  supabase: AdminClient,
  options: { dryRun: boolean }
): Promise<ImportReport> {
  // 1. 会期
  const session = await upsertBySlug(supabase, "council_sessions", councilSessions);

  // 2. タグ（label が一意）
  const insertedTags = await supabase
    .from("tags")
    .upsert(tags, { onConflict: "label" })
    .select("id, label");

  // 3. 議案。slug で突き合わせ、既存行の id を保つ
  const billRows = toBillInserts().map((bill) => ({
    ...bill,
    council_session_id: session.id,
  }));
  const insertedBills = await supabase
    .from("bills")
    .upsert(billRows, { onConflict: "slug" })
    .select("id, name, slug");

  // 4. 解説とタグ紐付けは既存の生成関数をそのまま使える。
  //    どちらも id + slug の配列を受け取る形になっている
  const contents = createBillContents(insertedBills);
  await supabase
    .from("bill_contents")
    .upsert(contents, { onConflict: "bill_id,difficulty_level" });

  const billsTags = createBillsTags(insertedBills, insertedTags);
  await supabase
    .from("bills_tags")
    .upsert(billsTags, { onConflict: "bill_id,tag_id" });
}
```

`createBillContents` と `createBillsTags` は `{ id, slug }` の配列を受け取る設計になっているため、DBから読み直した行をそのまま渡せる。開発シードと本番インポーターで解説データの生成経路が分岐しない。

### dry-run

`--dry-run` では書き込みの前に現在の本番行を読み、差分だけを標準出力へ出す。

```
会期      更新 0 / 新規 0
議案      更新 23 / 新規 0 / インベントリ外 0
  shinjuku-2026-r2-gian-42  publish_status: coming_soon -> published
  shinjuku-2026-r2-gian-42  is_review_completed: false -> true
  ...
解説      更新 69 / 新規 0
タグ紐付  更新 23 / 新規 0
利用者データ  interview_sessions 412件 / interview_report 88件（触れない）
```

差分の組み立ては純粋関数として `diff.ts` に置き、テストを書く。DBへ触る部分と分ければ、比較ロジックはローカルのSupabaseなしで検証できる。

### 破壊的シードのガード

インポーターを足しても、run.ts を本番の資格情報で叩けば同じ事故が起きる。run.ts の先頭で接続先を確認する。

```ts
// packages/seed/main/run.ts
const url = process.env.SUPABASE_URL ?? "";
const isLocal = url.includes("127.0.0.1") || url.includes("localhost");
if (!isLocal && process.env.ALLOW_DESTRUCTIVE_SEED !== "1") {
  throw new Error(
    `run.ts は clearAllData() で全データを削除する。ローカル以外では実行できない（接続先: ${url}）。` +
      "本番へ投入するときは import:production を使うこと。"
  );
}
```

`ALLOW_DESTRUCTIVE_SEED` を残すのは、本番相当の検証環境を作り直す用途が残るため。既定では通らない。

### ワークフロー

`seed_production.yml` は削除せず、2つに分ける。

- `import_production.yml`: dry-run を実行して差分をログに出し、`workflow_dispatch` の入力 `confirm: apply` があるときだけ本番へ書き込む。書き込み前に `supabase db dump --data-only` を取り、artifact として保存する（保持14日）。
- `seed_production.yml`: `ALLOW_DESTRUCTIVE_SEED=1` を明示的に渡す形へ変更し、name に「破壊的」と入れる。

投入後の Vercel 再デプロイは現行どおり deploy hook で行う。ただし [get-coming-soon-bills.ts](../web/src/features/bills/server/loaders/get-coming-soon-bills.ts) などの `unstable_cache` は `revalidate: 600` を持つため、再デプロイ直後でも最大10分は古い一覧が出る。2026-09-18 に注目議案が404のまま残った原因もこれである。インポーター完了時に `CACHE_TAGS.BILLS` を落とす revalidate エンドポイントを叩く手順まで含める（ROADMAP の「再シード完了時に関連キャッシュを即時無効化する」と同じ作業）。

## 復旧手順

1. 書き込み前の artifact（`supabase db dump --data-only`）を取得する。
2. `psql "$PRODUCTION_DB_URL" -f dump.sql` で戻す。一次資料層は上書き、利用者データ層はインポーターが触っていないため差分が出ない。
3. 戻した直後に dry-run を流し、差分が空であることを確認する。

この手順を `docs/DATA_PIPELINE.md` に追記する。

## 検証方法

ローカルで本番と同じ経路をなぞる。

```bash
# 1. 現行シードで初期状態を作る
pnpm db:reset

# 2. 利用者データが残ることを確かめるため、件数を控える
#    interview_sessions / interview_messages / interview_report

# 3. インベントリを coming_soon に戻した状態を一度作り、インポーターを流す
pnpm --filter @mirai-gikai/seed import:production:dry-run
pnpm --filter @mirai-gikai/seed import:production

# 4. 確認
#    - bills の id が 2. の時点と一致する
#    - publish_status が全件 published
#    - interview_sessions / interview_messages / interview_report の件数が不変
#    - 2回続けて流しても差分が空（冪等）
```

統合テストは `tests/supabase/seed/` に置く。既存の [r8-2-inventory-import.test.ts](../tests/supabase/seed/r8-2-inventory-import.test.ts) が `runId` 接頭辞で本番相当の投入を再現しているので、同じヘルパーを使う。押さえる項目は次の4つ。

- 2回流しても bills.id が変わらない
- インタビューとレポートの行が消えない
- インベントリ外の議案が本番にあっても削除されず、報告に出る
- 解説の本文を書き換えて流すと bill_contents が更新される

## 先に決めておきたいこと

インポーターの対象から interview_configs を外す判断は、本番で Admin がインタビュー設定を編集している前提に立っている。実際に本番の interview_configs が編集されているかを確認していない。編集実績がなければシード管理へ寄せた方が運用は単純になるので、本番DBを直接見てから確定する。
