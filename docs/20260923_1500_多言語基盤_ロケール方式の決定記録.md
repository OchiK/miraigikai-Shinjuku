# 多言語基盤: ロケール方式の決定記録（Phase 3 / Step 7B）

`docs/20260917_0723_implementation_plan_steps_3-7.md` の 7B は「コードを書く前に、ロケールのルーティングとライブラリ選定の決定記録を残す」ことを求めている。この文書がその記録。

関連: [I18N_AND_EASY_JAPANESE.md](I18N_AND_EASY_JAPANESE.md)、[ARCHITECTURE.md](ARCHITECTURE.md)「ルーティング」

## 1. 決定

| 論点 | 決定 |
|---|---|
| ロケールの持ち方 | **Cookie（`locale`）**。URL の `?lang=<locale>` があれば Middleware が Cookie に保存する |
| URL | 変えない。`/bills/[id]` などの既存 URL はそのまま |
| 自動判定 | しない。`Accept-Language` は見ない。初期値は常に `ja` |
| i18n ライブラリ | 入れない（下記 §3） |
| 対象画面 | 議案詳細（`/bills/[id]`）の題名・要約・本文のみ |
| 言語切替 UI | ヘッダーのメニュー（ハンバーガー）内にネイティブ `select`。全ページに出す（トップで選んでおけば、開いた議案がその言語で出る）。議案詳細以外では表示は変わらない |

### なぜ locale prefix（`/en/bills/...`）にしないか

ARCHITECTURE.md は prefix を推奨し、影響が大きければ Cookie から始めてよいとしている。今回 Cookie を選んだ理由:

- 難易度（やさしい／ふつう／くわしく）がすでに Cookie ＋ `?difficulty=` 方式で動いており、同じ仕組みに揃えると言語と難易度を同時に保てる。
- prefix にすると `app/` 以下のルートを `[locale]` 配下へ移す必要があり、`web/src/lib/routes.ts`、`routes.test.ts`、プレビュー、OGP、インタビュー、`revalidate` API の全経路に波及する。翻訳データがまだ1件もない段階で払うコストに見合わない。
- 翻訳が公開されるのは人が確認した議案だけで、当面ほとんどのページは日本語へのフォールバックになる。言語別 URL を検索エンジンに出す段階ではない。

prefix へ移すときは、`?lang=` 付き URL を `/[locale]/...` へ 301 する形で既存リンクを残せる。

### なぜ Accept-Language で自動切替しないか

翻訳は参考情報で、日本語が正本（I18N_AND_EASY_JAPANESE.md「翻訳原則」）。ブラウザ設定だけで日本語以外に切り替わると、本人が選んでいないのに参考訳を読むことになる。言語は本人が明示的に選んだときだけ切り替える。

## 2. 影響範囲

| 項目 | 挙動 |
|---|---|
| キャッシュ | `getBillById` のキャッシュ（議案 × 難易度）は変えない。翻訳の選択結果は別に `unstable_cache` で **議案 × 言語 × 難易度** をキーにキャッシュする（`web/src/features/i18n/server/loaders/get-localized-bill.ts`）。タグは `CACHE_TAGS.BILLS` で、既存の revalidate で一緒に消える。**翻訳の status を変える経路（今後の admin 画面・スクリプト）は必ず BILLS を revalidate すること**。しないと取り下げた翻訳が最大10分出続ける |
| canonical | 変えない（言語によらず `/bills/[id]`） |
| alternate / hreflang | 出さない。同じ URL で内容が Cookie により変わるため、hreflang を付けられない。prefix 移行時に追加する |
| sitemap | 変えない（URL が増えないため） |
| メタデータ・OGP | 日本語のまま。SNS のカードは正本の日本語を出す |
| プレビュー（`/preview/bills/[id]`） | 翻訳しない。admin 側のプレビュー（generated / stale も見られるもの）は別途 |
| インタビュー・レポート・チャット | 変えない。`getBillById` をそのまま使うため日本語のまま。チャットの多言語対応は 7C で扱う |
| API（`/api/*`） | 変えない |
| 認証コールバック | 影響なし（Cookie を読むのは議案詳細とヘッダーのみ） |
| `<html lang>` | `ja` のまま。翻訳を出している要約・本文の要素にだけ `lang` を付ける |

## 3. ライブラリを入れない理由

いま UI 文言として翻訳が必要なのは、注意書き・未翻訳の案内・言語切替の見出しの3種類だけ。`next-intl` などを入れると Middleware とルーティングの前提が増えるが、この量なら定数で足りる（`web/src/features/i18n/shared/messages.ts`）。ボタン・ナビなど UI 全体を翻訳する段階でライブラリを選び直す。その時点のバージョンと公式ドキュメントを確認すること。

## 4. 翻訳データ

テーブル: `bill_content_translations`（`supabase/migrations/20260923150000_create_bill_content_translations.sql`）

- `bill_contents` 1行 × ロケールごとに1件（`unique (bill_content_id, locale)`）
- ロケールは `en, zh-Hans, ko, ne, my, vi`。`ja` は正本なので持たない。`zh-Hant` を足すときは CHECK 制約と `packages/shared/src/i18n/locales.ts` の両方を変える
- `status`: `generated`（生成直後）／`reviewed`（人が確認済み）／`stale`（日本語が変わり再翻訳待ち）。`reviewed` には `reviewed_at` が必須
- 生成の記録: `model`、`prompt_version`、`translated_at`、`reviewed_at`、`reviewed_by`
- RLS 有効・ポリシーなし。読み書きは service role のみ

### 公開の条件

公開画面に出すのは、**`status = reviewed` かつ `source_hash` が現在の日本語から計算した値と一致する**翻訳だけ。ハッシュは保存時だけでなく**読み出しのたびに**照合する。`stale` への更新ジョブが漏れても、日本語が直った時点で古い翻訳は出なくなる。

### source_hash の定義

`packages/shared/src/i18n/source-hash.ts`

```
v1:sha256(JSON.stringify(["v1", difficulty_level, norm(title), norm(summary), norm(content)]))
```

`norm` は次の順に処理する。

1. Unicode NFC
2. 改行を LF に統一
3. 各行末の空白（半角・全角・タブ）を削除
4. 先頭・末尾の空白行を削除

全角・半角の変換はしない（数字や記号の意味が変わりうるため）。正規化を変えたらバージョンを上げる。既存の翻訳はすべて不一致になり、再翻訳が必要になる。

`bill_contents` には出典の改訂番号の列がないため、ハッシュには本文そのものと難易度を入れている。出典（PDF）の差し替えは、主張台帳と `bill-contents-revision.test.ts` を通じて本文の変更として現れる。

### フォールバック

`packages/shared/src/i18n/translation-fallback.ts`

1. 選んだ難易度の日本語に対する、公開条件を満たす翻訳
2. 「ふつう」の日本語に対する、公開条件を満たす翻訳
3. 日本語「ふつう」＋「翻訳がありません」の案内
4. 日本語「ふつう」が無ければ、選んだ難易度の日本語（日本語表示と同じもの）＋案内。7B の「日本語ふつうが無ければ内容なし」から変えた。日本語なら読める本文を、言語を切り替えたせいで消さないため
5. 翻訳の取得自体が失敗したとき（DB エラー）も、ページは落とさず 4 と同じ扱いにする

別の議案の翻訳やモデルの一般知識で穴埋めしない。案内には、実際に表示している言語と難易度を書く。

## 5. 翻訳を公開する手順（admin 画面ができるまで）

1. 翻訳を `status = 'generated'` で入れる。`source_hash` は翻訳元の日本語から `calculateSourceHash` で計算する
2. 日本語の読める確認者が、原文と突き合わせて確認する（数字・日付・法令番号・モダリティの強さ。やさしい日本語の4パスの監査と同じ観点）
3. 確認できたら更新する

```sql
update bill_content_translations
set status = 'reviewed', reviewed_at = now(), reviewed_by = '<確認者>'
where id = '<id>' and source_hash = '<確認した時点のハッシュ>';
```

`source_hash` を条件に入れるのは、確認中に日本語が直された場合に `reviewed` にしないため（7B「revision race」）。

SQL で直接更新したときは、キャッシュ（最大10分）が残る。すぐ反映させるには `/api/revalidate` で BILLS タグを消す。

シード（`packages/seed/main/bill-translations-data.ts`）には、承認第2号「ふつう」の英訳を1件、`generated` で入れている。ローカルで表示を確かめるときは、上の SQL で `reviewed` にする。シードの翻訳は本番インポーターの対象外。

## 6. 今回やっていないこと

- UI 全体の翻訳（ボタン・ナビ・見出し・エラー）
- 議案一覧・カードの題名の翻訳
- admin の翻訳管理画面（生成・確認・stale 化・プレビュー）
- `stale` への自動更新（読み出し時照合で公開は止まるので、表示上の安全性はこれに依存しない）
- 7言語すべてでの表示確認。7B の受入条件「監査済み議案1件を7言語で表示」は、翻訳と確認者がそろった段階で行う
- 各文字体系（デーヴァナーガリー、ビルマ文字）のフォントと改行の確認

### UI 文言の確認状況

`messages.ts` の6言語の文言と、シードの英訳は AI（Claude）が作成した。**どの言語もネイティブ話者の確認はまだ受けていない**。特にネパール語・ビルマ語は誤りの可能性が高い。そのため、どの言語の案内にも日本語の文を必ず並べ、日本語を正としている。
