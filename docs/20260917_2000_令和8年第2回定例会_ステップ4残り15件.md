## 3. 引用の機械照合

台帳の `evidence_excerpt` 606件（supported のもの全件）を、抽出したPDFテキストに対して機械照合した。

照合は次の手順による。

1. 引用と出典テキストの双方を NFKC 正規化し、空白をすべて除去する
   （`pdftotext` は日本語の文字間に空白を挿入するため）
2. 括弧・句読点などの表記ゆれを吸収する
3. 引用を、出典テキスト中に連続して現れる断片で被覆できるか調べる
4. **被覆率が100%であることを合格条件とする**

PDFの段組と表のため、引用が行またぎ・段またぎで分断されることがある。
そのため単純な部分文字列一致ではなく被覆検査を用いた。断片の途切れは抽出上の都合であり、
文字が出典に存在しないことを意味しない。

**結果: 606件すべてが被覆率100%で合格した。**

この照合の過程で、当初の引用のうち5件に実際の齟齬を検出し、修正した。

## 9. セルフレビューでの指摘と対応

AGENTS.md に従い `/review` を実行した。`codex` CLI が本環境にないため Codex レビューは実施できず、
テストガイドラインチェックとコード品質チェックの2本を実施した。

### 9-1. 解説本文の事実誤り（修正済み・最重要）

**第60号議案 normal の要約に「大767基・小30基」と書いていた。正しくは「大737基・小30基」である。**

767は737と30の合計値であり、要約の書き方では合計797基を意味してしまう。
本文の表と hard 側は正しく737基としており、**要約だけが誤っていた。**

修正: 「大737基・小30基（合わせて767基）」に改めた。
あわせて本文の「合わせて767基です。」を
「掲示板（大）737基と掲示板（小）30基で、合わせて767基です。」に改め、導出の内訳を本文でも示した。

**この誤りが検証を素通りした原因は、台帳が `content` の行しか持っていなかったことである。**
内容ハッシュは title + summary + content を対象にしているのに、台帳の被覆範囲は content だけだった。
また3-1の数値照合も本文に対する照合であり、767は本文に実在するため一致してしまった。

対応として、30変種すべてに `title` / `summary` の行を追加し（141行）、
被覆範囲をハッシュの対象と揃えた。
`bill-contents-revision.test.ts` に「各変種が title / summary / content すべての行を持つ」テストを追加し、
今後この穴が再発しないようにした。

要約の数値を改ざんする変異を入れて、ハッシュテストが実際に落ちることを確認済みである。

### 9-2. 「本文 → 台帳」方向が検証されていなかった（修正済み）

`bill-contents-revision.test.ts` は台帳に載っている変種だけを突き合わせていたため、
**台帳に行を書かずに解説だけ追加すると全テストが通ってしまう状態だった。**
ハッシュ固定の意図（本文を書き換えたら台帳の更新を強制する）を満たしていない。

当初は「ハッシュ固定の対象外は既存5件の10変種だけ」というテストで対象外集合を固定した。
完了監査ではステップ3の最終内容台帳にハッシュ列を追加し、期待値を対象外なしへ強化した。
解説を追加して台帳に書かない場合、または46変種の本文がレビュー済みハッシュと異なる場合は落ちる。

### 9-3. 台帳そのものの不変条件を追加（対応済み）

内容ハッシュは台帳の1列を書き換えるだけで通ってしまう。
ハッシュとは独立した歯止めとして、台帳の構造を検証するテストを追加した。

| テスト | 検出できること |
| --- | --- |
| 判定は supported か needs_source のいずれか | 未解決の contradicted / unsupported の混入、判定の綴り間違い |
| claim_id が一意 | 行のコピーミス |
| 主張・出典・引用・箇所がいずれも空でない | 記入漏れ |
| item_key がインベントリの安定識別子と一致 | 案件キーの誤り |
| 各変種が title / summary / content の行を持つ | 9-1の穴 |
| 本文に出てくる出典URLはすべて台帳に載っている | 本文に出典を足して台帳を放置すること |

いずれも変異テストで実際に落ちることを確認した。

### 9-4. 空振りしていたテストの実効化（修正済み）

`seed-associations.test.ts` の「タグ未設定の議案には bills_tags を作らない」は、
23件すべてにタグを付けた結果、未設定の経路を一度も通らなくなっていた
（`expect(billsTags).toHaveLength(23)` だけが残り、テスト名の不変条件を検証していなかった）。
タグ表に無い議案を明示的に混ぜ、その議案に関連付けが作られないことを見る形に直した。

### 9-5. 実装計画の受入条件に対応するテストが無かった（追加済み）

実装計画は「Normal/hard content joins to the intended bill **even when input order changes**」を
受入条件に挙げているが、**入力順を変えるテストは存在しなかった。**
`createBillContents` に逆順の配列を渡しても結果が変わらないことを検証するテストを追加した。
