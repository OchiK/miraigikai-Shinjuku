# 英訳の本番同期と確認手順

対象は区長提出の第63〜80号議案・認定第1〜4号の `normal/en`、計22件の下書き。2026-11-24 にローカル Supabase で同期・保護・選択復旧と、ローカル画面での承認・表示切替を確認した。本番の反映・承認・公開状態は未確認。

## 正本と保護

日本語が正本で、英語は参考訳。訳文は `packages/seed/main/bill-translations-r8-3-data.ts` に置く。`model=gpt-6.1-sol`、`prompt_version=r8-3-en-2026-11-24`。承認状態は DB（Admin）だけが持つ。Git と importer は `generated` だけを書き、人の確認を代行しない。

`source_hash` は翻訳した日本語の難易度・題名・要約・合成済み本文を指す。`source_snapshot` はその時の日本語、`imported_snapshot` は importer が最後に書いた英訳の題名・要約・本文。既存の R8-2 試作12行は本番同期対象に含めない。他言語、議員提出、`easy/hard` の訳を追加しない。

承認済み行と Admin 作成・編集行は、`updated_at` を含め保持する。未承認でも `imported_snapshot` が NULL または現在の訳文と異なる行は保護する。未承認・未編集の行だけが Git の変更で更新される。`stale` 行もこの未承認の規則に従う。インベントリ外は削除しない。dry-run 後の承認・編集も RPC の原子的条件で保護し、apply は実際に書いたキーだけを新規・更新として報告する。同文・同 hash なら保護対象の行でも「変更なし」と報告する。

## merge から承認・表示確認まで

以下は本番への適用手順。ローカル検証の結果とは分けて、本番での実施結果を記録する。

1. lint・型チェック・ビルド・単体テスト・統合テスト、ローカル DB 検証、独立レビューの結果を確認する。ユーザーが PR を merge すると `deploy_web.yml` が本番 DB に migration を適用するため、merge 自体もユーザーの作業とする。旧14引数版 RPC は維持され、新15引数版が英訳を扱う。
2. ユーザーが `Import Production DB (非破壊)` を `dry_run: true` で実行する。選んだ ref/commit とログを保存し、22件の新規・更新・変更なし・保護・インベントリ外、および日本語や他テーブルの差分を読む。保護だけなら「書き込み対象なし。保護された差分が N 件ある」となり、DB と Git の一致を意味しない。集計行は新規・更新・変更なし・インベントリ外の件数を示し、保護が1件以上あるときだけ末尾に「保護 N」を加える。保護が0件のときは、この欄を表示しない。
3. 意図した差分であるとユーザーが判断した場合、同じ ref で `dry_run: false`、`confirm: apply` を指定する。再度 dry-run が走り、バックアップ→確認者情報の置換→artifact 保存→import の順に進む。失敗した工程があれば後続に進まない。適用直前に変わった英訳は保護として報告されるので、dry-run との件数差も読む。
4. 承認前に、本番 DB に接続するローカル Admin の環境で `NEXT_PUBLIC_WEB_URL` が本番 Web の URL、`REVALIDATE_SECRET` が Web 側と同じ値であることを確認する。値やキーはログ・PR・文書へ貼らない。workflow 側のキャッシュ無効化には `WEB_PUBLIC_URL` と `REVALIDATE_SECRET` を使う。Admin は無効化失敗を承認エラーとして表示しないため、設定・表示の確認を省略しない。
5. `/bills/translations` で第3回定例会の一覧を開き、各 `/bills/<id>/translations` で日本語と英語の題名・要約・本文を全文対照する。金額、日付、条件、義務・許可、法令番号、議決用語、会派の集合と順序、「分からないこと」の全項目を確認する。訳語表は `translation-terms.ts`。会派の英語名は公式訳ではなく、日本語を併記する。
6. 人が確認を終えた行だけを Admin で承認する。現在の原文 hash と一致していることを確認する。`reviewed` は Git に戻さない。初回は1件を承認して表示確認してから残りへ進む。
7. 公開サイト `/bills/<id>?lang=en` で確認する。英語の題名・要約・本文が表示され、`easy/normal/hard` の各選択でも英語 `normal` へフォールバックすることを確認する。公式議案件名・会派賛否カードなどは現行どおり日本語で残る。本文の折りたたみも開く。承認・取消などの変更がすぐ反映されなければ、変更の経路を問わず、認証付き POST `/api/revalidate`（bills タグ）を実行して表示を再確認する。待つ場合は、10分経過後にページを2回以上読み込む。ローカルでは、直接 SQL で変更した後、10分経過後の最初の表示にも古い内容が残る場合があった。Admin の成功表示だけで公開確認としない。

## 日本語を改訂したとき

採決文を含む現在の日本語 `normal` と英訳を再び全文対照し、訳文を更新してから固定 `source_hash` を更新する。hash だけを更新しない。`source_snapshot` は seed の既存関数から現在の日本語を得る。seed のテスト・型チェックと最終検証を実行する。参照元の日本語変更を検知するため、hash を読み込み時に自動追従させない。

原文と hash が合わない承認済み英訳は読み出し時に公開対象から外れる。importer はその行を降格・上書きせず、保護として報告する。変更内容を人が確認して再承認する。

## 保護を外す・Admin 修正を Git に戻す

承認済み・未編集の行は、Admin の「承認を取り消す」または「下書き保存」で未承認に戻す。`imported_snapshot` と訳文が一致する場合だけ、次の import で更新できる。取消は人の判断で行い、差分を消すために自動実行しない。

Admin で編集・作成された行は Admin で直す。取消だけでは編集保護は解除されない。修正後の題名・要約・本文を同じ Git の行へ還流し、対応する日本語・hash・モデルの由来を確認する。Admin 修正をモデル生成と偽らず、修正経緯を PR に記録する。同文・同 hash なら「変更なし」となり、既存の承認記録や `imported_snapshot` を手で改ざんして同期権を奪わない。以後の修正もこの行は Admin で管理する。

## バックアップと選択復旧

対象10テーブルと復旧の規則は [DATA_PIPELINE](DATA_PIPELINE.md#復旧手順) を参照。`reviewed_by` は NULL 以外が `redacted` になり、誰が承認したかは artifact から戻せない。その他の列は保持する。生のダンプは upload しない。COPY ブロック・列・列数・終端が不正なら処理を止める。

artifact は隔離したローカル検証 DB と一時テーブルで読み、壊れた・消えた id だけを選択して復旧する。現在も残る reviewer、Admin 編集、バックアップ後の新規行・承認を保持する。一括削除や truncate は行わない。削除された承認行は本文・日時が復元されても reviewer は `redacted` になるため、必要なら Admin で再確認・再承認する。`council_member_questions` と `faction_stances` はバックアップの対象に含まれていない。
